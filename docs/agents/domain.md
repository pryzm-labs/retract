# Domain docs

Before exploring a feature, read the root `GLOSSARY.md` and any relevant architecture decision records in `docs/adr/`. If either is absent, continue. The `domain-modeling` skill creates these documents as terms and decisions are settled.

Use glossary terms in tickets, proposals, tests, and code. If a concept needs a new term, raise it during domain modeling. If a proposal conflicts with a recorded decision, cite the ADR and explain why the decision deserves another look.
